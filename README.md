# PISMO Web

Веб-клиент **PISMO**: тот же мессенджер и те же серверы, что в приложении
на ПК (`PISMO.exe`) и на Android (`pismo.apk`), только через браузер —
с любой машины, без установки.

Данные общие. Написанное с сайта видно на телефоне и на компьютере, и
наоборот: отдельной «веб-базы» нет, все клиенты работают с одной базой
`bdauth`.

---

## Зачем нужен бэкенд

ПК и Android ходят в MySQL **напрямую** — своего сервера у проекта
исторически нет. Браузер так не умеет: из веб-страницы нельзя открыть
TCP-сокет к базе. Поэтому здесь есть шлюз `backend/` — тот же слой
запросов, вынесенный за пределы страницы, плюс то, что нельзя отдавать
в браузер: доступ к базе и секрет LiveKit.

```
браузер ──HTTP+WebSocket──> backend ──MySQL──> bdauth  <── ПК, Android
   └──────────────────WebRTC────────────────> LiveKit <── ПК, Android
```

Медиа звонков идёт мимо бэкенда, напрямую в LiveKit — он только выдаёт
токен.

## Запуск

```bash
npm run install:all     # зависимости бэкенда и фронтенда
npm run build           # сборка фронтенда в frontend/dist
npm start               # сервер на :5000, он же отдаёт собранный сайт
```

Открыть `http://<адрес сервера>:5000`. Логин и пароль — те же, что в
приложении.

Для разработки — двумя процессами: `npm run dev:backend` (nodemon,
перезапускается на правку) и `npm run dev:frontend` (Vite на :5173 с
горячей перезагрузкой). Vite проксирует `/api` и `/socket.io` на
`localhost:5000`, так что настраивать ничего не нужно; если бэкенд поднят
не там — задайте `PISMO_BACKEND`.

Проверить слой совместимости, не поднимая базу: `npm test`.

### Микрофон, камера и https

Браузер отдаёт микрофон, камеру и демонстрацию экрана **только в
защищённом контексте**: это `https://` либо `localhost`. На обычном
`http://` по IP — например `http://192.168.0.10:5000` — объекта
`navigator.mediaDevices` не существует вовсе.

Из этого следуют две вещи, на которых легко потерять вечер:

* ошибка выглядит как `Cannot read properties of undefined (reading
  'getUserMedia')`, то есть как поломка в коде сайта, хотя дело в адресе;
* в настройках сайта камера и микрофон показаны серыми с подписью
  «Заблокировано в целях безопасности». **Это не разрешение, которое можно
  выдать** — интерфейса запроса в незащищённом контексте просто нет,
  нажимать там нечего.

Сайт теперь проверяет это сам: кнопки звонка приглушены, а в подсказке и в
полосе поверх экрана написано, что делать.

Варианта три, и они не равнозначны:

**1. С самого сервера — `http://localhost:5000`.** localhost считается
защищённым, звонки работают сразу. Годится, чтобы проверить, но только на
той машине, где запущен сайт.

**2. Флаг браузера — работает по сети и не требует ничего трогать.**
В Chrome `chrome://flags/#unsafely-treat-insecure-origin-as-secure`
(в Opera — `opera://flags`), вписать `http://192.168.0.10:5000`,
переключить в *Enabled* и перезапустить браузер. Флаг нужен на **каждой**
машине, откуда заходят.

**3. https на сайте — правильный путь, но одного его мало.**
Задайте `SSL_KEY` и `SSL_CERT`, и сервер поднимется по https:

```bash
SSL_KEY=/путь/key.pem SSL_CERT=/путь/cert.pem npm start
```

> ⚠️ **LiveKit тоже должен быть за TLS.** Со страницы по `https` браузер не
> пустит соединение на `ws://` — это смешанное содержимое. Значит
> `LIVEKIT_URL` обязан начинаться с `wss://`, иначе один запрет просто
> сменится другим: микрофон разрешат, а звонок не подключится. Сервер
> предупреждает об этом при старте.
>
> Поэтому вариант 2 — единственный, который даёт звонки **без** правки
> LiveKit.

Самоподписанный сертификат подойдёт (браузер один раз спросит подтверждение),
но для сети удобнее `mkcert`: он ставит локальный доверенный центр, и
предупреждений не будет.

### После `git pull` обязательно пересоберите фронтенд

`frontend/dist` — это результат сборки, он лежит в `.gitignore` и **через
git не приезжает**. Обновили код, перезапустили сервер — и продолжаете
видеть вчерашний сайт, потому что отдаётся вчерашняя сборка. Выглядит это
как «исправление не помогло», и ищут причину где угодно, только не здесь.

```bash
git pull
npm start          # из корня: сначала собирает фронтенд, потом поднимает сервер
```

Если поднимаете бэкенд отдельно (`npm run start:backend`), сборку нужно
обновить самому: `npm run build`. Сервер сверяет её с исходниками и, если
она отстала, пишет об этом в консоль и вешает красную полосу поверх
страницы — молча старую сборку он больше не отдаёт.

Что именно запущено, показывает `GET /api/health`: там есть время старта
сервера, время сборки фронтенда и признак `stale`.

### Если сайт пускает по логину, но содержимое пустое

Первым делом — консоль браузера (F12) и окно, где запущен фронтенд.

* **`livekit-client ... could not be resolved`** в выводе Vite — не
  доставлены зависимости. В папке `frontend` выполните `npm install` и
  перезапустите `npm run dev`. Одного `npm run dev` мало: пакеты сами не
  ставятся.
* **Красная полоса «Не удалось загрузить: …»** — запрос дошёл до базы и
  упал; текст ошибки в полосе и в консоли. Кнопка «Повторить» рядом.
* **Полоса «Подключение…» не гаснет** — не поднят бэкенд (`npm start` в
  отдельном окне) либо он слушает не на `localhost:5000`; тогда задайте
  `PISMO_BACKEND`.
* **Красная полоса «Открыта устаревшая сборка»** — см. раздел выше:
  выполните `npm run build`.
* **`Minified React error #31` про `[object ArrayBuffer]`** — в браузер
  ушли байты вместо текста. Такого больше быть не должно: наружу через
  сокет проходит только отрисовываемое (`backend/utils/wire.js`). Если
  всё же увидели — значит запущена старая сборка бэкенда, перезапустите
  его.

### Windows и Visual Studio

Сайт — это Node.js и React, отдельного проекта Visual Studio (`.sln`) у
него нет и не требуется: **нужен только Node.js**. Двойной щелчок по
`start-windows.bat` поставит зависимости, соберёт сайт и поднимет сервер.

Если удобнее работать из **Visual Studio Community**, она годится как
редактор с терминалом:

1. `File → Open → Folder…` и выбрать папку проекта (не «Открыть проект» —
   решения здесь нет).
2. `View → Terminal` (Ctrl + \`), затем те же три команды:
   `npm run install:all`, `npm run build`, `npm start`.
3. Для подсветки и отладки JavaScript поставьте в Visual Studio Installer
   рабочую нагрузку **«Разработка Node.js»**; после этого на
   `backend/server.js` можно нажать правой кнопкой → *Set as Startup Item*
   и запускать по F5 с точками останова.

> Не перепутайте с **PISMO.exe** — это `PISMO_MESSENDGER/PISMO.sln`
> (C#, net8.0-windows). Вот он открывается в Visual Studio как обычное
> решение и запускается по F5. Сайт — другой стек, и общего у них только
> база и сервер LiveKit.

### Настройка

Подключение к базе берётся из `ip.txt` в корне (формат ПК-версии):

```
server=5.181.23.167;port=3307;uid=user1;password=scent01;database=bdauth
```

Всё переопределяется переменными окружения — после ротации ключей
пересобирать ничего не нужно:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | из `ip.txt` | база `bdauth` |
| `LIVEKIT_URL` | `ws://<DB_HOST>:7880` | адрес уходит в браузер |
| `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` | как в клиентах | подпись токенов |
| `JWT_SECRET` | как в `JwtAuth.cs` | токен сессии |
| `PORT` | `5000` | порт сайта |
| `CORS_ORIGINS` | пусто (любой) | список доменов через запятую |
| `MAX_UPLOAD_BYTES` | 200 МБ | потолок вложения |

> **Про https.** Браузер не даёт странице с `https://` открыть `ws://`.
> На боевом домене `LIVEKIT_URL` обязан быть `wss://`, иначе звонки не
> подключатся — при этом на ПК и Android тот же `ws://` работает, и
> проблема выглядит как «звонки не работают только на сайте».

> **Про ключи LiveKit.** Пара по умолчанию лежит в публичном репозитории
> ПК-версии и считается скомпрометированной: имея её, кто угодно выпустит
> токен в любую вашу комнату. Ключи следует ротировать на сервере LiveKit
> и задать новые через переменные окружения.

## Что обязано совпадать с ПК и Android

Это не стиль, а условия стыковки. Расхождение здесь **не даёт ошибки** —
оно выглядит как «на сайте часть сообщений нечитаема» или «пароль верный,
но приложение не пускает». Тесты в `backend/test/compat.test.js` проверяют
каждый пункт.

| Механизм | Деталь |
|---|---|
| **Шифрование сообщений** | `enc:v2:` + base64(**nonce(12) ‖ tag(16) ‖ ciphertext**), AES-256-GCM. .NET отдаёт тег отдельно и кладёт его ПЕРЕД шифртекстом; Node и Java клеят `ct‖tag`, поэтому порядок задаётся вручную. Читается и легаси `enc:v1:` (AES-CBC) |
| **Ключ шифрования** | SHA-256 от `PISMO::message::secret::v1::do-not-change` |
| **Пароли** | `pbkdf2$<iter>$<b64 соль>$<b64 хеш>`, PBKDF2-HMAC-SHA256, 100 000 итераций |
| **Токен LiveKit** | HS256, Base64Url без паддинга. `canUpdateOwnMetadata` **обязателен** — без него сервер молча игнорирует смену атрибутов, и значки мьюта не работают |
| **Имя комнаты** | `call_<id сессии>` для звонка, `vch_<id канала>` для голосового канала |
| **identity участника** | id пользователя **строкой, без префиксов** — по нему ПК сопоставляет участников с плитками |
| **Значки мьюта** | атрибуты `mic` (**`"1"` = микрофон ВКЛЮЧЁН**, `"0"` = замьючен) и `deaf`. Инверсия на `mic` неочевидна; в базе при этом хранится обратное по смыслу `mic_muted` |
| **Область сообщения** | `scope`: 0 = ЛС, 1 = группа, 2 = канал сервера — общая колонка в `message_reactions`, `pinned_messages`, `message_edits` |
| **Пороги присутствия** | «не в сети» при `seen_ago > 40`, «бездействует» при `active_ago > 90` |
| **Упоминания** | `@логин`, `@название-роли`, `@все`/`@all`/`@everyone`/`@here`/`@здесь` |

### Что было исправлено относительно прежней версии сайта

Прежняя версия расходилась с приложениями в четырёх местах, и каждое
ломало стыковку молча:

1. **`ip.txt` смотрел на `85.174.248.59`** — этот сервер больше не
   обслуживается, всё переехало на `5.181.23.167`.
2. **Шифрование умело только `enc:v1`** (AES-CBC), а ПК и Android пишут
   `enc:v2` (AES-GCM). Сообщения из приложений показывались на сайте как
   `enc:v2:AAAA…`.
3. **Пароли хешировались bcrypt-ом.** `PasswordHasher` на ПК и Android
   отвергает всё, что начинается с `$2`, — сменивший пароль на сайте
   терял вход в приложение. Обратно так же: `pbkdf2$…` сайт не принимал.
   Теперь сайт пишет только `pbkdf2`, а читает все три формата и при
   первом успешном входе переводит старый хеш в `pbkdf2` — учётные записи
   со старого сайта чинятся сами.
4. **identity в LiveKit был `user_<id>`** вместо голого id — участник с
   сайта оставался на ПК неопознанным.

Плюс серверов и каналов на сайте не было вовсе, хотя на ПК и Android это
основной способ общения.

## Что умеет сайт

**Личные сообщения и группы.** Переписка постранично с догрузкой вверх,
текст, картинки, файлы, голосовые, ответы с цитатой, правка с историей,
мягкое удаление, реакции, закреплённые, «печатает…», непрочитанные,
блокировки, приватность ЛС «только друзья».

**Серверы.** Рельс серверов, текстовые и голосовые каналы, сообщения
каналов, `@упоминания` с подсветкой и отдельным счётчиком, бейджи
непрочитанного, роли и права (управление сервером, каналы, баны, кики,
мьюты), участники с группировкой по ролям, баны и разбаны, вместимость
голосового канала, заглушение уведомлений сервера.

**Голосовые каналы и звонки.** Личные и групповые звонки, вход в
голосовой канал, микрофон, камера, демонстрация экрана, наушники, плитки
участников со значками мьюта. Всё на LiveKit, в тех же комнатах, что ПК и
Android: позвонить с сайта на телефон — обычное дело.

**Прочее.** Друзья с заявками и поиском людей, профиль с аватаром,
присутствие, смена пароля.

### Чего на сайте нет

| Механизм | Причина |
|---|---|
| Запись видео-кружочков | контейнер `PSMOVID1` — свой формат ПК-версии; браузер его не пишет и не проигрывает. Присланные кружочки видны как вложение и скачиваются |
| Захват звука конкретного приложения | браузер такого не даёт; демонстрация экрана идёт со звуком вкладки |
| Оверлей поверх игр, трей, самообновление | нет эквивалента в браузере |

## Устройство

```
backend/
  config.js          конфиг: ip.txt, переменные окружения, адреса
  db.js              пул MySQL и хелперы запросов
  utils/
    crypto.js        enc:v2 (AES-GCM) в раскладке .NET + чтение enc:v1
    passwords.js     pbkdf2$, плюс чтение bcrypt и legacy-plaintext
    livekit.js       токены комнат, identity, имена комнат
    session.js       токен сессии (совместим с ws-сервером сигналинга)
    format.js        имена, описания вложений, разбор @упоминаний
  data/              слой запросов — порт репозиториев Android-клиента
    messages.js      ЛС и группы          servers.js   серверы и каналы
    presence.js      присутствие, голос   calls.js     сессии звонков
    social.js        друзья, профили      reactions.js pins.js scopes.js
  routes/
    auth.js          вход, регистрация, смена пароля
    media.js         вложения по HTTP с проверкой доступа
  socket/            обработчики событий: chat, servers, social, calls
  test/compat.test.js тесты совместимости (базы не требуют)

frontend/src/
  App.jsx            каркас, маршрутизация, звонки, присутствие
  lib/               api.js (REST), socket.js (события), format.js
  components/
    Auth.jsx         вход и регистрация
    Conversation.jsx окно переписки — одно на ЛС, группы и каналы
    Message.jsx      пузырь: вложения, реакции, упоминания, действия
    Sidebars.jsx     рельс серверов, список чатов, каналы, участники
    Panels.jsx       друзья, настройки, создание группы и сервера
    ServerSettings.jsx каналы, роли, участники, баны
    Call.jsx         звонки и голосовые каналы на LiveKit
```

Вложения ходят **по HTTP** (`/api/media/...`), а не через сокет: браузеру
картинку нужно поставить в `<img src>`, а файл скачать; двухсотмегабайтный
blob через socket.io оказался бы целиком в памяти вкладки. Доступ
проверяется на каждый запрос — ссылка вида `/api/media/0/123/image` это
просто число, и без проверки чужую переписку можно было бы вычерпать
перебором.

Права на сервере проверяются в обработчиках, а не только в интерфейсе:
спрятанная кнопка ничего не защищает, событие сокета отправляется руками
из консоли за десять секунд.
